# Portside

Local dev-server manager: Go daemon + CLI (`cmd/portside`) with an embedded React dashboard (`web/`). Built for macOS 26 or later; Linux is a preview that should keep working (keep code portable and Linux paths compiling and vetted) but is not a focus; Unix-only (process groups, PTYs).

## Commands

- `make build`: dashboard (`pnpm --dir web build` into `web/dist`) and `bin/portside`.
- `make check` runs the checks: `go vet ./...`, `go test ./...`, `pnpm --dir web build` and `go run ./scripts/notices -check`; CI adds `-race`. Tests cover config edits and stable automatic ports, discovery deduplication and Python proposals, directory warnings and terminal and editor launch arguments (per platform, with detected apps), Compose menu suppression, process-group termination, server handoff and adoption across an upgrade, log buffering and restoration, live readiness (including IPv6 and health failures), restart cancellation, rename continuity, stale launch settings, crash and config recovery, permission tightening of default and custom config and state locations, temporary worktree servers (naming, port choice, subdirectory mapping, persistence and removal; skipped without git), log replies, container attachment, failure and issue rules, persisted stop intent, event reconnect backoff, compose arguments and log WebSocket status/tail, and local authentication (the session cookie only on the dashboard host, signed requests accepted once and only for the daemon's epoch, clients refusing a daemon whose hello proof fails, single-use sign-in links on `127.0.0.1` without the dashboard host, forwarded to it and redeemed only for a connection of the same account, the session cookie refused from another account's connection with one owner lookup per connection, `next` paths without control characters or backslashes, unproved refusals not shown by the client, the dashboard host rotating on a cold start and kept across a handoff, old hosts getting the hint page without the new one, cookies bound to one host, reply proofs failing for an altered body, a busy `[::1]` refusing the start, connection owners from `/proc/net/tcp` and `lsof` output), sharing between devices (pairing codes and keys, request signatures and server proofs, the peer guard, port mirrors giving way to local listeners, chosen local ports, resuming a connection, forwarded ports in the supervisor, Tailscale status and Serve parsing), coding-agent setup (item states, registration through the agents' own CLIs, faked on PATH, never a foreign skill replaced), the rendered launchd and systemd definitions, and the app's CLI contracts (`daemon info --no-start` exit codes, `setup --json` and `--apply`, and the checks before `daemon stop` signals an older daemon); they need no Docker, Tailscale, external network or real config; readiness checks use isolated loopback listeners. `pnpm --dir web check:contrast` verifies WCAG AA for every theme.
- `make notices` regenerates `THIRD_PARTY_NOTICES.txt` (`scripts/notices`: Go modules linked into `./cmd/portside` for every release platform, production npm packages from `web/node_modules`, theme credits kept in the script). Run it after changing Go or npm dependencies or adding a theme; it fails on an unrecognized license or an uncredited theme file. The file ships in the archives (`.goreleaser.yaml`), the app's `Contents/Resources` and the dashboard as `/licenses.txt` (a Vite plugin in `web/vite.config.ts`).
- `make dev-daemon` (isolated daemon on :7980, config and state in `.dev/`; `PORTSIDE_DEV_ORIGIN=5173` lets the dashboard host at that port write), `make dev-open` (sign the browser in; prints the Vite address; the dashboard host is new on each cold start of the dev daemon), `make dev-ui` (Vite on port 5173 proxying `/api` and `/auth`; open it at `http://<dashboard host>:5173`, where the session cookie applies). Clients check the daemon's proof of the token in `<state>/auth-token` and then sign every request with it (never sent); `curl -H "Authorization: Bearer $(cat <state>/auth-token)"` works for manual calls. Browsers get a session cookie through `portside open`, valid only on the dashboard host in `<state>/dashboard-host`, which is new on every cold start.
- Try changes against an isolated instance: `PORTSIDE_CONFIG=/tmp/x/portside.toml PORTSIDE_STATE_DIR=/tmp/x/state` with `port = <free port>` in that config. The user's real daemon runs on :7878; do not stop it or its servers.

## Layout

- `internal/app`: product name, ID, service label (the macOS app's bundle ID is `<label>.app`, read from here by `scripts/build-macos-app.sh`), default and fallback ports, env prefix. The only place the product name is defined. The version comes from `-X main.version`; the release workflow takes the repository and tap owner from GitHub.
- `internal/config`: TOML loading and validation (`config.go`, which also owns `IsComposeCommand` and the compose stop timeout `ComposeStop` used by supervisor and discovery), comment-preserving field edits of `[servers.<name>]` tables (`edit.go`, `edit_values.go`; `SpecDir` is how every writer records a server's directory), automatic port persistence on daemon load, last-good startup fallback (`recovery.go`), starter file (`starter.go`: `StarterRoot` picks the projects folder by counting projects in commonly named folders).
- `internal/supervisor`: process lifecycle in PTYs (`supervisor.go`), the launch environment and PATH lookup (`env.go`), process-group termination (`terminate.go`), listener ownership and killing foreign listeners (`listeners.go`), the periodic sampling loop (`stats.go`), continuous readiness and loopback selection (`readiness.go`), scrollback and log files (`logbuf.go`), environment from the account's login shell (`shellenv.go`; see `docs/configuration.md` "Environment" for how it is read and refreshed, and which values stale checks ignore; `ReadLoginShell` also feeds `doctor`), per-project tool environments (`toolenv.go`: direnv, devbox, mise, fnm or nvm around the server's shell, or the server's `wrap`), process identity by `ps` start time in the C locale (`procstart.go`: `processStart`, `sameStart` for values saved by older daemons), CPU/memory sampling, persisted state and orphan recovery (`state.go`), handing live servers to a re-executed daemon and adopting them (`handoff.go`), temporary copies of a server for other git worktrees (`worktree.go`; kept in state, never in the config), JSON `View`.
- `internal/docker`: Docker Engine API client over the active context's endpoint (`endpoint.go`: context resolution, TLS settings and the engine socket candidates; `dial.go`: unix, TCP with TLS, and SSH through `docker system dial-stdio`; `client.go`), the live container monitor with events and stats (`monitor.go`; `Publishing` lists the containers behind a port, which `publishedBy` in `internal/server/containerowners.go` matches to the starting server so the supervisor can treat a hidden listener as that compose stack's port; ssh:// engines poll stats one-shot instead of a stream per container), engine start detection and engine-specific errors (`engine.go`), compose service and project jobs (`job.go`), and deliberate stop persistence (`stopstate.go`). Compose jobs shell out to the docker CLI (or `docker-compose`, `podman compose`, `podman-compose`); lifecycle and logs use the Engine API.
- `internal/server`: HTTP API, WebSockets (`/api/events`, `/api/servers/{name}/terminal`), host/origin guard and `*.localhost` proxy (`server.go`), routes (`routes.go`; log and terminal streaming in `terminal.go`, config editing in `configroutes.go`), opening folders, editors and terminals and the detected apps behind the Settings pickers (`desktop.go`; macOS apps by bundle ID through Launch Services, Linux commands on PATH), plain-text log replies with search and size limits (`loglines.go`). Authentication (`auth.go`): requests signed with the token for the daemon's epoch (random per start; `/api/health` answers a challenge with the epoch and a proof, and authenticated replies carry a proof of their status and body, buffered in `proved` in `server.go`; WebSocket upgrades the short proof), a bearer token for manual use, single-use sign-in links (`/api/auth/code` returns them on `http://127.0.0.1:<port>/auth` so process arguments never show the dashboard host, plus the dashboard address separately) forwarded to the dashboard host and redeemed there only on a connection from another process of the daemon's account (`fromOwner`, `ports.ConnectionOwner`: `/proc/net/tcp{,6}` on Linux, `lsof` on macOS, refused elsewhere; looked up once per connection through `ConnContext`, which the daemon's `http.Server` sets, and failed lookups are tried again), and the dashboard session, whose cookie is accepted only on such a connection too: the dashboard is served only at `http://d-<24 hex>.localhost:<port>` (new on every cold start, carried across an upgrade in `handoff.json` when all listening sockets came over, new when the daemon had to listen anew; reserved by `config.IsDashboardLabel`), the cookie (`HMAC(token, "dashboard session", host)`) is accepted only there, other `d-<hex>.localhost` hosts get the sign-in hint (`staleDashboard`, marked with `X-<product>-Sign-In`, which makes the app's window sign in again), and `127.0.0.1`/`localhost` serve the API plus that hint without revealing the host. `internal/signing`: the one request-signing scheme (HMAC over method, request URI, time, nonce, body hash and epoch; time window, nonce cache, epoch check, and challenge proofs `HMAC(key, "server", challenge, epoch)`, for whole replies with the status and body hash added; each MAC kind has its own part count), used by local clients with the token and by paired devices with their key; `macos/Sources/Portside/Signing.swift` mirrors it. The JSON shapes here are the dashboard's contract.
- `internal/daemon`: daemon process (lock, listeners on `127.0.0.1` and `[::1]`, the latter required unless the system has no IPv6 loopback, also after a handoff; signals; port choice in `port.go`: when the config sets no `port`, `listenConfigured` tries the port kept in `<state>/auto-port` (`SavedPort`), the default, then `app.FallbackPorts` (7879-7899, 17879-17899), counting anything that accepts connections on either loopback address as taken, and keeps a fallback port in `auto-port`, never in the config; it refuses with `ErrPortHeld` (a clean exit) instead of moving when this product of this account holds the port (`client.PortHolder`); a taken explicit port fails naming the holder; an upgrade that cannot bind a newly configured port keeps the inherited sockets (`takeOverListeners`); writes `<state>/daemon.port` so clients find a daemon on another port than the config says). In-place upgrades (`upgrade.go`): `POST /api/upgrade` (denied to peers) checks the given binary, then the main loop writes `<state>/handoff.json`, keeps the lock, listening sockets and server terminals open across `syscall.Exec` and re-executes in the same pid; the new daemon finds the file through a nonce in the environment, adopts the servers before `Recover` and serves on the inherited sockets. On success the request gets no reply; `daemon restart` then waits for the new `startedAt` and version, and falls back to stop and start for a daemon without the route. The stop marker `<state>/stopped` is written by a deliberate stop (`/api/shutdown` without `restart`, `daemon stop`, `service uninstall`) and removed by every daemon start except one taking over from an upgrade, which then stops instead (a stop wins over a pending upgrade); while it exists the macOS app polls `daemon info --no-start` instead of starting a daemon. `daemon info` is the app's contract: JSON on stdout, exit 3 when no daemon runs (`--no-start`), 4 with `configError` when the config does not load; `verified: false` with the claimed version when what answers cannot prove itself (the app then offers a restart). A daemon that loses the lock exits 0, and so does a shutdown, so launchd and systemd only restart crashes. `internal/client`: CLI-to-daemon HTTP client with auto-spawn (through the login service when it runs this daemon); it proves the daemon first (`Ping` repeats the handshake; `Health.Verified`), signs every request and WebSocket dial (`DialWebSocket`) for the proven epoch, checks reply proofs, repeats the handshake once after a 401, and never sends the token; an unproven daemon gets `ErrUnverified` and nothing signed. `Ensure` starts a daemon also when a foreign program or another account's daemon holds the port and no daemon holds the state lock (`DaemonRunning`), then follows `daemon.port`; it starts none while this product of this account holds the port (`PortHolder` in `holder.go`: only an lsof/ss owner of the same uid whose command is this product's binary counts, never a pid claimed by the health reply or an ssh tunnel; state directory from the open lock file) and never one from an agent sandbox (`Sandboxed`, `ErrSandboxed`). `daemon restart` accepts only a verified daemon and follows `daemon.port` while it comes up. `daemon restart` and `stop` send a daemon from before verified requests SIGTERM after checking it is this user's listener on the port at `127.0.0.1` and at `::1` when something answers there and that it holds this state directory's lock (`shutdown` and `daemonListens` in `internal/cli/daemoncmds.go`). `doctor` checks that the daemon itself answers on `[::1]`.
- `internal/cli`: commands (`browser.go`: the browser `open` uses, or none so the sign-in link is printed). `internal/mcpserver`: MCP tools over stdio (servers, containers, logs with `match`). `internal/agentskill`: the agent skill (`skill.md`, a template filled from `internal/app`), installed by `portside skill install` and refreshed by the main daemon on start; keep it in line with the CLI and MCP tools. `dirs.go` locates the agents' directories (`CLAUDE_CONFIG_DIR`, `CODEX_HOME`, `GEMINI_CLI_HOME`, read from the login shell when the process has no terminal); Codex gets `~/.agents/skills` unless an earlier copy is in `$CODEX_HOME/skills`. `internal/agentsetup`: the one list of coding-agent setup items (Claude Code, Codex and Gemini CLI MCP registration through their `claude`/`codex`/`gemini mcp add` CLIs, found on PATH or the login shell's PATH, with a stable path to this binary; the skill per agent), their states and how each is applied; used by `setup` (`internal/cli/setup.go`: y/N prompt, `--yes`, `--json`, and `--apply <ids> --yes` printing JSON results, which is the app's contract; `--print-mcp` prints the `mcpServers` entry for other clients, `--print-prompt` the setup request for a coding agent from `prompt.md`; keep it in line with the CLI). The dashboard shows the same items through `GET /api/agents` and `POST /api/agents/apply` (`internal/server/agents.go`, refused to paired devices; `web/src/features/agents`) on its empty page and in Settings, `doctor` (read-only; `--fix` applies missing and outdated items) and the app. It never edits agent config files itself and never replaces a foreign skill file. `internal/service`: launchd/systemd (install, start and restart through the service, systemd linger check; the definition pins the config and state locations; on Linux install and start import the desktop session variables into the user manager, without a `DISPLAY` forwarded over SSH, and without systemd install returns `ErrNoSystemd` with a shell-profile hint); `service uninstall` first stops whatever daemon runs, also one started outside the service, the same way as `daemon stop`, then removes the service. `internal/paths`: config, state and log locations (`XDG_CONFIG_HOME`/`XDG_STATE_HOME` honored on Linux only, so the macOS app, CLI and launchd agree; `legacy.go` moves what earlier versions left there on macOS, run first by `cli.Main`, only directories with the product's marker files and nothing else, and not while a daemon or the launchd agent uses them; `service install` moves them through `MoveLegacyForService` before writing the agent), and their modes (`modes.go`: `0600` files, `0700` directories, and `Restrict`, which the daemon runs on start to drop group and other access; the default config and state directories are tightened with their contents, a custom config only as the file, and a custom state directory only itself, its logs and the files the product keeps in it (`stateEntries`; add new top-level state files there); never parents or unrelated files). `internal/discover`: project detection (walk, naming, configured-command filtering and shared port suggestions in `discover.go`; Node and Deno scripts, with script indirection and shell word parsing, in `node.go`; workspace roots and their package globs in `workspace.go`; Python and its runner in `python.go`; other frameworks and Compose in `backends.go`) for the API and CLI. Detection stays conservative: an automatic port only for a command known to take `{PORT}` or read `$PORT`, otherwise `noPort`; project-derived names (folders, script names) enter a generated command only when they match a plain-word pattern. `internal/ports`: listener lookup via `lsof`/`ss`.
- `internal/tailnet`: Tailscale status and Serve entries through the tailscale CLI. `internal/share`: lets the owner's paired devices in (Serve entry, listener and request checks in `share.go`, pairing codes and device tokens in `devices.go`). `internal/remote`: connects to another device's daemon (discovery, pairing, connecting and resuming in `peers.go`; `/api/peer` relay, `/api/tunnel` port tunnels and forwarded ports in `remote.go`; the macOS check for a local listener next to a forwarded port in `probe.go`; the saved connection and chosen local ports in `store.go`). The CLI reaches the connected computer through `client.On` (`--on`, `internal/cli/computers.go`), MCP tools through their `computer` argument. `internal/server/remote.go` holds their routes, the peer handler and `<name>.<computer>.localhost`; `web/src/features/remote` and the `/api` base switch in `web/src/api/client.ts` are the dashboard side.
- `internal/server/containers.go`: container routes; logs, shell and job output stream over the same terminal WebSocket protocol as servers. Container ownership is in `containerowners.go`: explicit project names (servers sharing one ordered by the closest directory), closest Compose working directory, or a local CLI project ID from repository-bounded config lookup, over configured and temporary servers. It also watches container issues and uses the supervisor notifier guard.
- `web/`: dashboard (Vite, React, xterm.js); `web/embed.go` embeds `web/dist`. Themes: `web/src/styles/themes/*.css` are copied unchanged from the shared ui-theme catalog; Portside's own per-theme tokens live in `web/src/styles/semantic.css` and terminal palettes in `web/src/theme/terminal.ts`.
- `macos/`: Swift menu bar app (AppKit status item + SwiftUI panel, WebKit dashboard window; the first launch opens the dashboard, whose empty page is the getting-started page, and Settings > Connect Coding Agents opens the dashboard at `#settings/agents`; `scripts/onboarding-preview.sh` runs a second instance as a new user sees it, with its own config, state, daemon and temporary home); `scripts/build-macos-app.sh` assembles `dist/macos/Portside.app` with the Go binary in `Contents/Helpers/portside`. `make app-install` installs it (update steps in README "Install", under "Other ways to install").
- `packaging/homebrew/portside.rb.tmpl`: cask rendered by the release workflow (placeholders `__VERSION__`, `__SHA256__`, `__REPO__`, `__BUNDLE_ID__`, `__SERVICE_LABEL__`). Arm64 only. `uninstall` only quits the app, because `brew upgrade` runs it too, so servers keep running (the caveats tell users to stop the daemon first); `zap` runs after the app is removed, so it removes the launchd service, sends SIGTERM to any other `portside` process and waits, then trashes config and state. `tap-README.md` is the README of the account's tap repository `<owner>/homebrew-tap` (`brew install --cask <owner>/tap/portside`), which other projects may share, so the workflow writes only `Casks/portside.rb`; the tap needs that first commit, since the release workflow clones it and pushes the cask. Release notes are the version's section of `CHANGELOG.md` plus an install footer (`release.yml`); a tag without a section fails.
- `.github/workflows`: third-party actions are pinned to commit SHAs with the tag in a comment, and GoReleaser to an exact version; update both together with the tag comment. CI runs Linux checks on pushes and pull requests; the macOS build runs on demand and in `release.yml`.
- `README.md` is the short landing page (highlights, install, quick start, links); the user documentation lives in `docs/` by topic (configuration, CLI, dashboard, coding agents, containers, other computers, how it works, security, development). Keep each fact in one place.
- `SECURITY.md`: private vulnerability reporting, supported versions and scope; keep its scope in line with `docs/security.md`.
- `design/`: app icons (`design/brand`: tug light/dark), compressed concept and icon explorations (`design/explorations`; full-size originals live untracked in `design/originals`), screenshots used by the README and `docs/` (`scripts/screenshots.sh`; `--portfolio DIR` writes light/dark pairs and renders the menu bar panel offscreen with the app's `--render-panel=PATH` flag). The menu bar glyph is drawn in code (`macos/Sources/Portside/StatusIcon.swift`).

## Constraints

- Never use the em dash character in code, comments, UI copy (English or Polish) or docs.
- Keep the product name out of identifiers; derive user-visible names and env vars from `internal/app`.
- macOS builds target Apple Silicon only (arm64) and macOS 26 or later; keep `macos/Package.swift`, `macos/Resources/Info.plist`, the cask template, the CI runners, `scripts/build-macos-app.sh` and `.goreleaser.yaml` in line with the README requirements.
- Config edits must go through `internal/config` so comments survive and invalid text never reaches disk.
- Files written into the config or state directories use `paths.FileMode` and directories `paths.DirMode`: configs can hold secrets in `env` and logs can hold credentials. State files are replaced through `paths.WriteFile` (a fresh private temporary file, then rename); the config through `internal/config`.
- Process termination always targets the process group (`-pgid`): SIGINT, then SIGTERM, then SIGKILL.
- pnpm is pinned to 12.6.0 with `minimumReleaseAge: 1440`; ask before adding `trustPolicy` exceptions.
